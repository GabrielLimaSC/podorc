# Contribuição

## Branches

- `main`: releases/sprints demonstráveis aprovadas.
- `dev`: integração do trabalho aprovado.
- `feature/<task-id>`: uma task, um dono, criada a partir de `dev` atualizada.

Commits e pushes diretos em `main` ou `dev` não fazem parte do fluxo. Toda mudança chega por pull request.

## Pull requests

1. O autor abre PR de `feature/<task-id>` para `dev`.
2. O outro Dev faz a revisão cruzada e aprova ou solicita mudanças.
3. O Tech Lead confere o `done_when`, o diff e reproduz os testes relevantes.
4. O merge em `dev` ocorre somente após aprovação técnica e dentro da autorização vigente do Gabriel.
5. Ao concluir uma sprint, o Tech Lead abre PR de `dev` para `main`; Gabriel decide a integração.

Quem escreveu a task não faz o próprio merge: a revisão cruzada do outro Dev e a revisão técnica do Tech
Lead são passos obrigatórios, registrados no corpo do PR. Como o repositório usa uma única conta GitHub,
essa separação é disciplina de processo, não um `approve` de outra conta.

## Identidade e mensagens

Formato de commit: `tipo(escopo): descrição em português`.

O repositório tem uma identidade única: todo commit, push, PR, review e merge é feito como
`Gabriel Lima <gabrielsiqueira311@gmail.com>` no Git e pela conta `GabrielLimaSC` no GitHub. Não há
identidades por papel nem contas separadas; o trabalho aparece como do Gabriel.

Nunca incluir `Co-authored-by`, `Signed-off-by`, `Claude-Session`, "generated by", emoji de robô, menção a
Claude/Codex/assistente, atribuição automática ou nome inventado — em commit, corpo de PR, review ou log de
teste. O repositório não deve conter rastro de contribuição de IA. Antes de qualquer push/PR/review/merge,
a sessão valida `git config user.name`/`user.email` e `gh auth status`.

## Evidências

O PR informa task, `done_when`, testes executados, cenário manual, limitações e riscos. Build verde sozinho
não substitui teste do comportamento real.
